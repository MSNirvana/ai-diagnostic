# Skill 验收标准 v1（Skill 生产线总闸门）

- 日期：2026-06-15
- 状态：v1，随前 10 个真实案例迭代
- 作用：定义"一个合格诊断 skill 长什么样"。Loop 1（Skill 生产线）的所有候选必须过这道闸门才能进 registry。

> **这份文件是 100 个 skill 产能的命门。** 文章里的 Goodhart 定律：当验证标准变成目标本身，AI 会针对验证器优化而不是针对真实价值优化（"测试要全过 → 把失败的测试删了"）。所以下面每条断言都要问一句：**AI 能不能用"看似满足、实则无用"的方式骗过它？** 能，就说明这条标准没写对。

---

## 一、验收哲学：三层考试

一个 skill 候选要过三层，越往下越难自动化：

| 层 | 考什么 | 谁判 | 能否自动化 | 否决权 |
|---|---|---|---|---|
| **L1 结构合规** | 输出能不能被系统消费 | 代码断言 | 完全自动 | 任一条挂 = 直接淘汰 |
| **L2 内容质量** | 像不像一个真专家说的话 | 代码断言 + LLM 判卷 | 半自动 | 通过率 < 阈值 = 打回重做 |
| **L3 业务价值** | 老板拿去用了有没有用 | 人审 + 真实案例复盘 | 不可自动 | 上线前人签字 + 上线后追踪 |

**核心原则：L1+L2 用机器把 90% 的废品挡在门外，把人的精力留给 L3 这种机器判不了的判断。**

---

## 二、L1 结构合规（机器判，硬否决）

每条都是布尔断言，**全过才进 L2**。任一条失败 = 候选直接淘汰，反馈给起草 agent 重做。

| # | 断言 | 为什么 | 防什么 Goodhart |
|---|---|---|---|
| S1 | 输出能被 `ModuleResult` 反序列化 | 不合 schema 系统根本渲染不了 | — |
| S2 | `signal ∈ {red, yellow, green}` | 前端按信号着色 | 防止模型自创"orange" |
| S3 | `evidence` 条数 ≤ 3 | 表层不堆数据（设计铁律） | — |
| S4 | `actions` 条数 ≥ 1 且 ≤ 5 | 至少 1 条可执行，多了不聚焦 | 防止塞 20 条凑数 |
| S5 | 每条 `evidence` 的 text 和 source 都非空、非"未注明"、非占位符 | 来源缺失 = 不可信 | 防止 source 全填"行业报告"蒙混 |
| S6 | `conclusion` 非空且 ≥ 10 字 | 结论先行是产品的脸 | 防止给一个字"差" |
| S7 | `evidence_package.confidence ∈ [0,1]` 且 `confidence_reason` 非空 | 置信度要可解释 | — |
| S8 | 声明的每条 required `data_requirement`，当输入缺失时必须出现在 `data_requests` | 缺数据要老实说，不能瞎编 | **防核心作弊：数据不够却硬给结论** |

---

## 三、L2 内容质量（机器判 + LLM 判卷，软否决）

20 道考题里 **≥ 90%（18/20）** 通过才算过 L2。低于阈值，把失败样例和原因反馈给起草 agent，最多重做 5 轮。

### 3.1 机器可判的断言（assertions.py 实现）

| # | 断言 | 防什么 Goodhart |
|---|---|---|
| C1 | `evidence` 里至少 1 条含具体数字 | 防止全是"较高""偏弱"这种无锚定形容词 |
| C2 | `evidence` 引用的数字必须在输入 facts 里真实出现（或来自 benchmark） | **防最严重作弊：编造数据** |
| C3 | 每条 `action` 含动作动词（停/改/加/切/降/升/限/设/查/补…） | 防止"加强协同""提升效率"这种正确的废话 |
| C4 | `conclusion` 不含模板腔短语（见禁用词库） | 防止套用固定句式 |
| C5 | `action` 不与 `conclusion` 字面重复 | 防止把结论复制成行动凑数 |
| C6 | 行业 KPI 命中：conclusion/evidence 至少命中 1 个该行业核心 KPI 词 | 防止给通用废话、不懂这行 |
| C7 | 置信度校准：无 evidence 时 confidence < 0.5；≥2 条 evidence 且有 benchmark 时可 ≥ 0.7 | 防止空手套白狼还报高置信度 |
| C8 | 信号-结论一致性：signal=red 时 conclusion 必须含负面判断词；green 时不得只报问题 | 防止信号和文字打架 |

### 3.2 LLM 判卷（独立 agent，反 Goodhart 主防线）

由**独立的判卷 agent**（最好换一个模型）扮演专家+挑剔老板，对每个样例打分。判卷 agent 看不到起草 agent 的推理过程，只看最终输出。

| # | 维度 | 判卷标准 |
|---|---|---|
| J1 | 说人话 | 这段结论是真分析，还是模板拼接？老板读得懂吗？ |
| J2 | 洞察深度 | 有没有讲出"非显而易见"的判断？还是把输入复述了一遍？ |
| J3 | 行动可执行 | 每条 action 是否具体到员工明天能动手？ |
| J4 | 证据-结论咬合 | 证据是否真支撑结论？还是贴了几个不相关数字？ |
| J5 | 行业专业度 | 像不像懂这个行业的人说的？有没有外行硬装内行的破绽？ |

## 四、L3 业务价值（人审 + 真实案例，不可自动化）

机器永远判不了"这个建议对老板真有用吗"。这层必须保留人和真实客户。

### 4.1 上线前人审（5 分钟/候选）

reviewer（最好是真咨询顾问）扫一遍，签字才上线：
- 行业术语对不对（机器查不出"把毛利说成净利"这种内行错误）
- 判断纪律对不对（这行的"什么算好/坏"标准是否符合常识）
- 语气是否符合面向老板的定位
- 有没有合规雷区（医疗/金融/教育类的监管红线）

### 4.2 上线后真实追踪（7/14/30 天）

**这是唯一可信的 PMF 信号，不可压缩、不可自动化。** 接进客户成功 SOP：
- 老板有没有真的把这个 skill 的建议拿去开会/执行
- 执行后 KPI 有没有改善
- 复盘偏差进 Loop 3 的 hard negative 样本池

> 文章金句对照：Boris 几千 agent 夜里无人值守跑代码，因为代码有 type-check/test/lint 三道**客观**验证。咨询没有客观验证，所以前 5-10 家真客户**必须保留人在 loop 里**。这条不能省。

---

## 五、四道防 Goodhart 的结构性设计

1. **判卷 agent 与起草 agent 分离**（不同模型最好）——学生不能自己批卷子
2. **C2 数字溯源断言**——编造数据是咨询最致命作弊，单独设硬断言
3. **S8 缺数据必须申报**——堵住"数据不够也硬给结论"
4. **L3 真实追踪不可删**——验证器再全也只是代理指标，真实 KPI 才是终极目标

## 六、阈值与降级（可调参数）

| 参数 | v1 取值 | 说明 |
|---|---|---|
| L1 通过要求 | 100% | 任一条挂即淘汰 |
| L2 通过线 | 18/20 (90%) | 低于则重做 |
| 重做上限 | 5 轮 | 5 轮仍不过 → 标记 `failed`，转人工 |
| 测试样例数 | 20/skill | 红5/黄5/绿5/缺数据5 |
| 人审 | 必须 | 上线前签字，不可跳过 |

失败降级：5 轮不过的候选不丢，存入"难产样本库"，作为起草 prompt 的反面教材。
